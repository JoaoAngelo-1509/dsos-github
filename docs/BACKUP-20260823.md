## 2. Banco de dados (projeto `goitceguoynlwvtexbdu`)

Tudo vive no schema **`backup_20260823`**, dentro do próprio banco.

Esse schema **não tem nenhum privilégio para `anon`/`authenticated`** — nem
`USAGE` no schema, nem `SELECT` nas tabelas. Isso é intencional e obrigatório:
ele contém cópia de `pc_senha` e `usuario_ti` (hashes de senha), e o schema
`public` tem *default privileges* que liberariam acesso automaticamente a
qualquer tabela nova. Verificado após a criação: `has_schema_privilege` e
`has_table_privilege` retornam `false` para as duas roles.

> `otp_ti` aparece nesta lista porque existia no momento do backup. A
> verificação em duas etapas foi **removida do projeto depois disso**, então a

Restaurar os dados de uma tabela:

```sql
BEGIN;
TRUNCATE public.ticket CASCADE;
INSERT INTO public.ticket TABLE backup_20260823.ticket;
COMMIT;
```

> Rode o `TRUNCATE ... CASCADE` com atenção à ordem das FKs (`pc` e
> `usuario_ti` são referenciadas por `ticket`; `ticket` por `mensagem`).
> Conferir antes com um `SELECT count(*)` dos dois lados.

Recuperar a definição original de uma função:

```sql

WHERE tipo = 'function' AND nome = 'rpc_login_pc';
```

Ver todas as policies como estavam:

```sql
SELECT nome, ddl FROM backup_20260823._ddl_snapshot
WHERE tipo = 'policy' ORDER BY nome;
```

Para reverter uma função, basta executar o `ddl` retornado — já vem no
formato `CREATE OR REPLACE FUNCTION`, então sobrescreve a versão atual.


resolução de chamados, chat e o painel de logs estão todos funcionando.
